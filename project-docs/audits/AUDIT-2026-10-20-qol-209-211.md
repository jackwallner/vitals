## Findings

### CONFIRMED

**C1. Prompt-card transition replace-all leaked into two Settings info callouts.** Fixed in `fix: restore Settings info callout transition`.
- `Vitals/Views/DashboardView.swift:3744` (generic ⓘ callout) and `:4236` (Body Profile callout).
- c291a73 swapped the dashboard prompt card's transition for a delayed fade. The same block was also pasted onto both `SettingsInfoCallout` sites, comment included ("slid it over the date and gear ... the ring below makes room first"). Settings has no date, gear or ring. At the Body Profile site the comment and modifiers were also mis-indented.
- Failure scenario: tap any ⓘ in Settings. The explanation now appears after a 0.2s delay as a bare fade, where it used to slide in with the row. This was never meant to change, and the comments describe a different screen, which reads as vibe coded.
- Fix: both callouts are back to `.opacity.combined(with: .move(edge: .top))`. The dashboard prompt card keeps its new transition. Proof: run `...064417-18014` built Vitals with the fix. This is a cosmetic revert with no logic, so no unit test.

**C2. `testLargeWidgetAddAndTap` passes without checking the widget or the tap.** Not fixed (test design, needs a local simulator to iterate).
- `VitalsUITests/AuditFeaturesUITests.swift:484-519`. The only assertion is that the widget gallery search field exists. After that, the test blind-taps by coordinate, writes screenshots to the runner's `/tmp`, and calls `waitForExistence` without asserting the result.
- Failure scenario: a large widget that fails to render, or a `totalcalories://metric/*` Link that routes nowhere, still passes. Its green result is not evidence for item 2.

### PLAUSIBLE

**P1. `totalcalories://recap` opens the Vitals+ weekly recap for free users.** `Vitals/App.swift:870` calls `WeeklyRecapCoordinator.shared.request()` without a Pro check, and `WeeklyRecapView` has no gate. Before this change, only the Pro recap notification could reach it. Now anyone can by typing the URL in Safari or Shortcuts. Low reach. A one-line `StoreService.shared.isPro` guard would close it.

**P2. Goal Reached shows ON before notification permission has been asked.** `GoalSettings.swift:796` defaults it to true, and the binding (`DashboardView.swift:~3820`) only reads OFF when status is `.denied`. With `.notDetermined`, Settings shows the switch on while nothing can be delivered. The design leaves the ask for the first goal hit, so this may be intended, but the switch overstates the state. Separately, existing users who already granted permission for the weekly recap will start getting goal-reached pushes after updating, without opting in.

**P3. Siri reports "0 calories" when the device is locked and today's cache is missing.** `Vitals/Intents/VitalsAppIntents.swift:9-18`. Live HealthKit is unreadable while locked, and if no today row has been cached yet (first query after midnight before any refresh), `TodaySnapshot.load()` returns `(0, 0, 0)`. Siri then says "You've burned 0 calories today, 0% of your goal." Throwing a "Unlock your iPhone to read Apple Health" error would be more honest. Not reproducible on gh-sim (no lock state).

**P4. The Lock Screen inline widget has no stale or unavailable state.** `VitalsWidget/VitalsWidget.swift:550`. The circular and rectangular accessories dim stale data, but inline shows yesterday's numbers as if current, and shows "0 cal · 0 steps" when `dataAvailable == false`. If every metric is hidden, the text is empty beside an icon. This is consistent with how the circular accessory handles `dataAvailable`, but it is the only family with no staleness cue at all.

**P5. The evening reminder silently skips scheduling when today's cache is missing.** `Vitals/Utilities/DailyNudgeService.swift:98` (`guard let stats = ... else { return }`). Enabling the reminder, or moving its time, before any today refresh has run leaves nothing pending, and there is no fallback to a live read. On a real device the cache nearly always exists, but this is what both evening-reminder UI tests hit on the runner.

**P6. The Evening Reminder upsell pitches streaks, not the reminder.** `Vitals/App.swift:354` maps `.eveningReminderToggle` to the `.streaks` focus. Tapping "Evening Reminder" opens "Keep your streak alive / Goal streaks" (seen in a run `...064417-18014` attachment), and the pitch never names the reminder the user tapped. This is intentional per the code comment, but it may confuse users.

**P7. A notification tap does not dismiss MainTabView-level sheets.** `Vitals/App.swift:856-872` only posts `vitalsDismissSettings`. If a trial pitch, recap or review sheet is up when a `metric/*` link arrives, the History push happens underneath it. Minor.

### REFUTED (checked, no bug)

- **Notification delegate (iOS 27 crash fix)**, `Vitals/App.swift:430-461`: `willPresent` calls its completion synchronously. `didReceive` captures the handler `nonisolated(unsafe)` and calls it on main after routing inside `MainActor.assumeIsolated`. Correct.
- **RootView split**, `Vitals/App.swift:84-171`: the `WindowGroup` closure no longer reads observed state on the release path. The singletons are still created after `init` (the computed `goals`/`store`). `onOpenURL`, the foreground and significant-time-change hooks, and every watch-sync `onChange` moved over intact. The DEBUG-only screenshot harness branch still reads `goals.appearance` unobserved, which is harmless.
- **GoalSettings `isLoading` guard**, `Shared/Services/GoalSettings.swift:~717-828`: every load-time assignment to `calorieGoal`/`stepGoal` happens before `isLoading = false`. Screenshot and forceSetup overrides come after it, but they are DEBUG/screenshot only.
- **`VITALS_RESET_STATE`**: compiled out in Release (`DebugLaunchConfig` `#else` returns false).
- **Goal-reached dedupe**: `DailyNudgeService` and the dashboard share the `goalCelebration.calorieDate`/`stepDate` keys, and both key on `DailyHealthRecord.key` (`yyyy-MM-dd`, gregorian). A goal already celebrated on screen is not pushed. The in-app toast after a background push is the intended "answer on open".
- **Evening reminder copy and math** (`DailyNudgePlanner`): resting burn still to come is netted out, gaps round up, the streak comes from `MilestoneCalculator.currentStreak`, which starts at yesterday (so "Keep your N-day streak" is right on an open day), and nothing is sent once goals are on track. Covered by `DailyNudgePlannerTests` (passing in run 1).
- **Deep link parsing**: `DeepLink(url:)` handles today, recap and `metric/{calories,steps,net,macros}`, and rejects foreign schemes and unknown routes (`DeepLinkTests`, passing). Net and Macros links are dropped for users without the feature (`DashboardView.swift:1583`). Cold launch is handled by `onAppear` in both MainTabView and DashboardView as well as `onChange`. `CFBundleURLTypes` registers `totalcalories` (confirmed by the system open prompt on the runner).
- **Widgets**: the large widget's week query uses string keys that sort lexically. Progress is clamped. Every Link target is a valid `DeepLink`. `primaryLink` falls back to `today`.
- **App Intents** run on MainActor, `openAppWhenRun = false`, and fall back to the App Group cache (default file protection `completeUntilFirstUserAuthentication`, so the cache can be read while locked after first unlock). The phrases include `.applicationName`, and `INAlternativeAppNames` adds "Total Calories".
- **Instant goal saving**: commits happen on focus loss and on goal-toggle flips, and on close as before. Invalid drafts keep the last good value. `onAppear` state seeding cannot write a stale draft. UI tests `testGoalsSaveWithoutClosingSettings` and `testTypedGoalCommitTiming` pass.
- **Recalibration** (`GoalRecalibration`): 14 completed days, 10 or more with data, excluded days and today ignored, a 14-day settle after any goal change, a 30-day snooze on Keep, and results clamped to validation ranges (calories 500 to 50,000, steps 100 to 500,000). Runs for free users too (`checkGoalStreakMilestone` is not Pro-gated). Covered by `GoalRecalibrationTests` (passing).
- **App Review**: no treat, cure or diagnose language in any new copy (notifications, cards, Siri dialog, info callouts). Review prompts: `requestReview()` stays on the positive-moment path with no pre-question. The first goal moment gives way to the notification card, and the tracker keeps the ask pending (5.6.1 OK).
- **Alternate icons**: `AppIcon-A/B/C.appiconset` are each one universal 1024 px PNG, RGB with no alpha. `ASSETCATALOG_COMPILER_ALTERNATE_APPICON_NAMES` and `INCLUDE_ALL_APPICON_ASSETS` are set in both `project.yml` and the pbxproj (Debug and Release). With these settings actool writes `CFBundleIcons`/`CFBundleAlternateIcons` into the built Info.plist, so the source `Info.plist` correctly carries none. There is no picker UI, which is right for an App Store icon test, and no stray `setAlternateIconName`. Note: the primary `AppIcon` PNG is RGBA (this predates the scope, and earlier uploads were accepted).
- **Swift 6 concurrency**: `DailyNudgeService` and the router are MainActor. `onTodayCacheSaved` is typed `@MainActor ... async`. No new `nonisolated(unsafe)` beyond the completion handler. Both runs built clean under strict concurrency.

## Not verified, and why

- **Large widget, inline widget and Lock Screen rendering, and widget-tap routing**: gh-sim cannot place widgets, and the one UI test that tries asserts nothing (C2).
- **Recalibration card and notification card visuals, background goal-reached delivery, evening reminder firing**: HealthKit seeding failed on the fresh runner ("Couldn't load"), so there were no numbers to act on.
- **Deep-link routing on screen**: `simctl openurl` stops at the system "Open in ...?" confirmation, so screenshots show the dialog, not the destination.
- **Alternate icon contents in the built Info.plist**: not inspected (it would need a `gh-sim build --products` run). Verified from build settings and asset catalog only.
- **Siri and App Shortcuts, locked-device fallback**: no Siri and no lock state on the runner.
- **iOS 27 crash fixes on a real device**: the runner simulator is iOS 27.0, and neither run crashed, but the original crash path (a tap on a real notification from a cold start) was not exercised because the notification tests could not get permission.
