## C1. Watch complication drops the minus sign on negative net deficit

**Where**: `VitalsWatchWidget/WatchComplication.swift:29-39` (`ComplicationFormat.shortNetDeficit`)

### Bug
```swift
let prefix = value >= 0 ? "+" : ""   // ← "" for negatives
let absVal = abs(value)
return prefix + compactWholeNumber(absVal)
```
A surplus of `-499` renders as `"499"` (no sign) across all four accessory families. Color is the only signal, which fails for color-blind users and on monochrome faces.

### Fix
```swift
let prefix = value >= 0 ? "+" : "−"   // U+2212 minus, or hyphen if preferred
```
Keep `absVal = abs(value)` so magnitude formatting is untouched.

### Plan
1. Change one ternary in `shortNetDeficit`.
2. Audit for any caller that was already prefixing a sign externally (none — single call site is each `NetDeficit*View`).

### Why it's safe
- Purely additive to the display string.
- The `abs(value)` in `compactWholeNumber` was already correct — the wholeness of "K" and "M" rounding is preserved.
- Tinting logic (`netDeficit >= 0 ? positive : negative`) is unchanged.
- Cannot change widget timelines, cannot affect cache, no auth involved.

### Validate
- Unit test table:
  - `shortNetDeficit(499, .accessoryCircular)` → `"+499"`
  - `shortNetDeficit(-499, .accessoryCircular)` → `"−499"`
  - `shortNetDeficit(-10_500, .accessoryRectangular)` → `"−10K"`
  - `shortNetDeficit(0, .accessoryInline)` → `"+0"`
- Visual diff on a watch simulator complication gallery with `foodCalories > totalCalories`.

## C3. "Enable Health" / "Open Settings" recovery banners are unreachable

**Where**:
- `Vitals/Views/DashboardView.swift` — `HealthNotice` enum, `refresh()` body (lines 826-931), `handleHealthNoticeAction` (lines 732-760)
- `VitalsWatch/Views/TodayView.swift` — `WatchHealthNotice` enum, `refresh()` (lines 262-327), `handleHealthNoticeAction` (lines 232-252)

### Bug
`healthNotice = .accessNeeded` is never assigned. `healthNotice = .accessBlocked` is only assigned inside `handleHealthNoticeAction(.accessNeeded)`, which the user can only trigger by tapping the `.accessNeeded` banner that is never shown. The `.accessBlocked` recovery button deep-link to Settings is therefore dead code: users who deny HealthKit see only a `.noData` banner with an "Open Health" button, never the Settings deep-link.

### Fix
In `refresh()`, after `synchronizeAuthorizationStateForFetching()` but before attempting the query, classify the current HealthKit state and assign the appropriate notice:

```swift
let reqStatus = await healthKit.authorizationRequestStatus()
switch reqStatus {
case .shouldRequest:
    // Never prompted OR at least one type still undetermined.
    if !healthKit.isAuthorized { healthNotice = .accessNeeded }
case .unnecessary:
    // System already prompted. If the fetch returns all-zero repeatedly
    // AND cache is empty, treat as blocked.
    // (Decided below after the fetch based on isAllZero + cache state.)
    break
case .unknown:
    break
@unknown default:
    break
}
```

Then refine the post-fetch block: if `stats` is all-zero, cache is empty, and `reqStatus == .unnecessary`, set `healthNotice = .accessBlocked` instead of `.noData`. Keep `.noData` for the case where auth is granted but HealthKit hasn't ingested anything yet (newly granted, before first sample).

Apply symmetric logic to the watch, where `.accessBlocked`'s text already explains the Watch-app-on-iPhone flow. Also add a visible button (or tappable body) for `.accessBlocked` on the watch — currently the watch only wires a button for `.accessNeeded` (line 151-158).

### Plan
1. Introduce a pure helper `classifyHealthNotice(stats:cached:reqStatus:) -> HealthNotice?` on both platforms (small, deterministic).
2. Call it from `refresh()` after `fetchTodayStatsWithRetry()` returns, before the existing assignment.
3. On the watch, extend the notice block to also show a guidance text (no button) when `.accessBlocked` — the Watch app on iPhone is the only recovery path.
4. Keep the existing `.noData` / `.cachedData` / `.loadError` assignments for their current semantics.

### Why it's safe
- Adds transitions into states that already exist (icons, copy, buttons are all wired in the enum's computed properties).
- Doesn't change the happy path: when auth is granted and data is present, `healthNotice = nil` still wins.
- `authorizationRequestStatus()` is already called inside `handleHealthNoticeAction(.accessNeeded)` — we're just calling it earlier.
- New classification is deterministic and only reads immutable inputs.

### Validate
- Fresh install, tap Don't Allow on HealthKit sheet → banner reads "Health access needed" with "Enable Health" button → button triggers request again OR reports `.accessBlocked` if system declines to re-prompt.
- Device with previously denied HealthKit → banner reads "Health access is off" with "Open Settings" → deep-link opens Settings → Privacy → Health → Total Calories.
- Happy path: auth granted, data present → no banner.
- Auth granted but no samples in HealthKit (simulator brand-new user) → `.noData` banner with "Open Health".

## C4. `dietaryEnergyAccessDenied` is rendered but never set to `true`

**Where**: `Vitals/Views/DashboardView.swift:864-884, 915-929`, plus UI sites at `:658` and `:686`

### Bug
Every assignment sets `dietaryEnergyAccessDenied = false`. When Net Deficit is on and the user denies dietary energy read, `fetchDietaryEnergyToday()` returns `0` **without throwing** (documented HealthKit denied-read behavior). The dashboard then sets `dietaryEnergyReady = true, foodCalories = 0` and silently renders the total-burned as a fake deficit. The "Health isn't sharing food calories…" footer and related accessibility summary are unreachable.

### Fix
We can't detect denial directly (Apple's API doesn't expose read-auth status), so use a probe:

1. Add `HealthKitService.fetchHasAnyDietarySampleEver() async throws -> Bool` that runs `HKSampleQuery` with `HKObjectQueryNoLimit=1` and no date filter for `dietaryEnergyConsumed`.
2. After `fetchDietaryEnergyToday()` returns, if today is 0 kcal AND the user just turned on Net Deficit (or `!dietaryEnergyReady` on first post-auth run) — *and* the system's auth-request status for dietary is `.unnecessary` (meaning the sheet was already shown) *and* the probe returns zero samples — treat as denied.
3. Cache the denied verdict in a `@State` for the session to avoid per-refresh probes.

This heuristic has a false-positive on users who authorized dietary but have literally never logged food. Mitigate by only flagging denied when the *probe result* is "no samples ever AND `.unnecessary` AND foodCalories today == 0". A user who authorized and has any historical sample will correctly be classified as granted.

### Plan
1. Extend `HealthKitService` with a cached `dietaryLikelyDenied: Bool?` + a one-shot probe method.
2. In Dashboard `refresh()` Net-Deficit branch, after the first fetch, call `healthKit.evaluateDietaryReadAccess()` once per session.
3. On denied verdict: `dietaryEnergyAccessDenied = true`, `dietaryEnergyReady = false`.
4. On probe failure or inconclusive result: leave `dietaryEnergyAccessDenied = false` (we default to "assume granted") — same behavior as today.
5. Mirror on watch? Out of scope: watch has no denial UI.

### Why it's safe
- Default behavior (dietary authorized, food logged) is unchanged — the 0-kcal probe is only run after the first all-zero fetch.
- Net Deficit-off users never touch the dietary code path; this change is gated behind `goals.showNetCalories`.
- The `.evaluateDietaryReadAccess()` call is idempotent and caches.
- Failure of the probe itself falls back to current behavior.
- No widget / complication path affected (watch NetDeficit already has its own 0-kcal edge cases tracked in H7).

### Validate
- Deny dietary auth in Health → toggle Net Deficit on → dashboard shows "Food sharing denied" footnote, `netDeficitNumericReady == false` → placeholder dash rendered.
- Authorize dietary, log zero food today → dashboard shows "No food logged today" footnote, numeric zero.
- Authorize dietary, log 1500 kcal today → numeric deficit renders normally.
- Authorize, then revoke in Settings, then re-launch → next session detects denial again.

## H1. `HistoryView.loadHistory()` has no re-entry guard

**Where**: `Vitals/Views/HistoryView.swift:477-515` (plus callers at `:271`, `:282`, `:288`, `:295`)

### Bug
Unlike `DashboardView.refresh()` (guarded at `:827`), History does not. `.task` and `.onReceive(willEnterForegroundNotification)` can both fire on the same foreground event, launching concurrent HealthKit statistics queries that race into `@State records`. Result: flicker when the slower query finishes last, plus doubled HealthKit quota consumption.

### Fix
Mirror the Dashboard pattern:
```swift
private func loadHistory() async {
    guard !isRefreshing else { return }
    isRefreshing = true
    defer { isRefreshing = false }
    ...
}
```
Also reset `isLoading = false` *only* on first completion so repeated entries don't re-hide content.

### Plan
1. Add guard at function top.
2. Keep existing `isLoading` logic — guard runs regardless of first-vs-refresh.
3. Ensure the `refreshable { await loadHistory() }` pull-to-refresh still feels responsive (SwiftUI's refreshable honors reentry — adding the guard is harmless since it simply no-ops the second call).

### Why it's safe
- Single-flight semantics match Dashboard's refresh, already battle-tested in production.
- `isRefreshing` is a `@State` on the main actor → no thread safety concern.
- `refreshable` pull-to-refresh and tab-change `.task` entry continue to work; subsequent entries are no-ops until the in-flight load completes.
- No change to the data schema or HealthKit query shape.

### Validate
- Foreground the app repeatedly on the History tab → confirm only one `fetchHistory` at a time via log instrumentation.
- Tap a period → pull to refresh during fetch → confirm no duplicate concurrent queries.
- First load still shows `ProgressView`; subsequent manual refresh still shows small indicator.

## H4. Goal celebration can fire on cold launch from stale `prevTotal`

**Where**: `Vitals/Views/DashboardView.swift:762-801`

### Bug
On cold start, `@State` values are 0. First `applyStats` sees `prevTotal = 0 < calGoal && newTotal >= calGoal` → haptic fires. Idempotency key (`GoalCelebration.shouldCelebrateCalories`) usually saves us, but only if the user opened the app earlier today. A user who never opened iOS today but already earned the goal (watch-only usage) will get one extra buzz on first foreground — which may feel right, but it's not the code's intent (intent is to celebrate *the transition*, not the open).

Minor severity because `GoalCelebration` persists in UserDefaults; the extra buzz only fires once per day.

### Fix
Option A (ship): change the condition to `prevTotal > 0 && prevTotal < calGoal && newTotal >= calGoal` — require a real prior reading. Pair with a small `@State didHydrate: Bool` so the first stats assignment is considered the baseline, not a transition.

Option B: drop `prevTotal` gate entirely and lean fully on `GoalCelebration.shouldCelebrateCalories` for dedupe (since that's per-day persistent). Removes the anti-transition logic but makes semantics "once per day when first seen ≥ goal", which matches most user expectations.

Ship Option B for simplicity.

### Plan
1. Remove `prevTotal < calGoal` predicate.
2. Rely on `GoalCelebration.shouldCelebrateCalories(for: todayKey)` alone.
3. Same for steps.

### Why it's safe
- `shouldCelebrateCalories` is already the source of truth for dedup.
- Worst case: a user who already crossed the goal today from the watch gets an iPhone haptic the first time they open the app today. That's desired — the "transition" abstraction was a proxy for "first observation."
- Cannot double-fire (persistent key).

### Validate
- Open iPhone app in the morning before reaching goal → earn goal → one buzz.
- Close, reopen later → no buzz.
- Kill app overnight, earn goal via watch only → open iPhone next morning → one buzz on first load.
- Next day → cycle repeats.

## H5. Watch `WKApplication.scheduleBackgroundRefresh` may not pair with `.backgroundTask(.appRefresh("vitals.watch.refresh"))`

**Where**: `VitalsWatch/App.swift:100-102, 139-148`

### Bug
SwiftUI's `backgroundTask(.appRefresh(_:))` modifier expects an incoming task whose identifier matches the string. `WKApplication.shared().scheduleBackgroundRefresh(withPreferredDate:userInfo:scheduledCompletion:)` is the legacy WatchKit API and does not take an identifier. If these two are incompatible, the handler may never receive the scheduled delivery and the watch only refreshes on its 1-hour timeline policy and on foreground.

### Fix
Two options, pick one:

**Option A (minimal)**: Drop the identifier — use `.backgroundTask(.appRefresh)` (unnamed). This matches what WKApplication's scheduler emits.

**Option B (modern)**: Switch scheduling to `BGTaskScheduler.submit(BGAppRefreshTaskRequest(identifier: "vitals.watch.refresh"))` which *does* match the modifier's identifier. Keep identifier in sync with `BGTaskSchedulerPermittedIdentifiers` in `VitalsWatch/Info.plist` (not currently present for watch).

Ship Option A as a one-line change that preserves existing scheduling semantics (and legacy-watch compatibility). Option B requires plist edits and more churn.

### Plan
1. Change `.backgroundTask(.appRefresh("vitals.watch.refresh")) { ... }` to `.backgroundTask(.appRefresh) { ... }` (omit identifier).
2. Add one log line in `handleBackgroundRefresh` that also logs the WKRefreshBackgroundTask-style start so we can confirm delivery on device.

### Why it's safe
- WKApplication's scheduling API is preserved, same cadence.
- `.appRefresh` without identifier is the documented matcher for legacy-style unnamed requests.
- No plist, no entitlement, no identifier-list changes.
- If the modifier today is already being invoked, dropping the identifier doesn't break delivery. If the modifier is *not* being invoked today (the bug), dropping the identifier fixes it.

### Validate
- Install on a real Apple Watch, let the app be backgrounded.
- Trigger a refresh window via Xcode: Debug → Simulate Background App Refresh? (on watch: use `WKApplication.shared().scheduleBackgroundRefresh(withPreferredDate: Date().addingTimeInterval(20))`).
- Observe `logger.info("background refresh started")` in Console.app filtered by `com.jackwallner.vitals.watch`.
- Without the fix, no log in ~60s after the scheduled time; with the fix, log appears.

## H6. `enableBackgroundDelivery` registers a dietary-energy observer unconditionally

**Where**: `Shared/Services/HealthKitService.swift:358-414`

### Bug
`types` always includes `dietaryEnergyConsumed`. If the user never authorized dietary reads, `enableBackgroundDelivery(for:frequency:)` errors ("Authorization not determined") and the observer query immediately errors too. Noisy logs for Net-Deficit-off users on every launch.

### Fix
Gate the dietary observer behind an explicit positive signal:
```swift
var types: [HKObjectType] = [.activeEnergy, .basalEnergy, .stepCount]
if goals.showNetCalories || dietaryEnergyLikelyAuthorized {
    types.append(HKQuantityType(.dietaryEnergyConsumed))
}
```
`dietaryEnergyLikelyAuthorized` = "we've successfully fetched at least once this install".

### Plan
1. Introduce a `UserDefaults` boolean flag `dietaryBackgroundDeliveryEnabled` set `true` once after the first successful dietary fetch.
2. In `enableBackgroundDelivery`, conditionally append the dietary type.
3. In `fetchDietaryEnergyToday` success path, set the flag and re-invoke `enableBackgroundDelivery` if it was previously off.
4. Never attempt to register dietary background delivery when Net Deficit is off *and* the flag is false.

### Why it's safe
- `enableBackgroundDelivery` is already guarded by `observerQueriesInstalled` (one-shot per process) — we're only *reducing* what gets registered.
- When the user flips Net Deficit on, the current Dashboard code calls `requestDietaryAuthorization()`; we can chain `enableBackgroundDelivery()` after a successful grant.
- Existing non-dietary observers (active/resting/steps) unaffected.

### Validate
- Fresh install with Net Deficit off → inspect Console → no "dietary not authorized" log entries.
- Toggle Net Deficit on, grant auth → observe one successful `fetchDietaryEnergyToday` → subsequent launches register the dietary observer cleanly.
- Toggle Net Deficit off again → subsequent launches still register (flag persists — that's OK; auth still valid).

## M5. Actor-isolation borrow of `self.store` in `queryStatisticsCollection`

**Where**: `Shared/Services/HealthKitService.swift:544-574`

### Bug
Captures `self.store` into a `nonisolated` context. Flagged in prior audits. Compiles today; may warn/error under Swift 6 strict concurrency.

### Fix
Add `@MainActor` to the helper:
```swift
@MainActor
private func queryStatisticsCollection(...) async throws -> [Date: Double]
```
and remove `let store = self.store` — use `self.store` directly. If we need to block the actor less, pass the store as a parameter from a `nonisolated` wrapper:

nonisolated private func queryStatisticsCollection(store: HKHealthStore, ...) async throws -> [Date: Double]

## M6. Custom range persistence can restore an invalid window on boot

**Where**: `Vitals/Views/HistoryView.swift:17-31` + `:284-297`

### Bug
`savedCustomEnd()` defaults to `.now` when unset. If a user saved a 30-day window yesterday, `customEnd` now points to a past `.now`. The `CustomRangeSheet`'s validator (≤ 730 days, start < end) only runs when the sheet is opened. On boot we `loadHistory(from: customStart, to: customEnd)` with possibly-invalid values.

### Fix
On load, clamp:
- If `customEnd > .now`, set `customEnd = .now`.
- If `customStart > customEnd`, set `customStart = DateHelpers.daysAgo(6)`.
- If `(customEnd - customStart) > 730.days`, clamp `customStart = customEnd - 730.days`.

Apply in `HistoryPrefs.savedCustomStart/End` getters or in `HistoryView.onAppear`.

### Plan
1. Add a `HistoryPrefs.sanitize()` that reads, clamps, writes-back if needed, returns the valid pair.
2. Use in place of the two individual getters.

### Why it's safe
- Pure normalization; never widens beyond user intent.
- Idempotent.
- No observable change for users within valid windows.

### Validate
- Set custom range, force-quit, shift device clock forward 3 days, relaunch → confirm history loads without "Maximum range is 2 years" phantom error or empty data.
